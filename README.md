# jepx-arb-lab

JEPXスポット市場の価格を蓄積し、**「完璧に予測できたら蓄電池でいくら稼げたか」** を算出する実験リポジトリ。

制御レイヤーは意図的に含めていません。対象（低圧／高圧／系統用）が決まる前に着手できる範囲を先に固め、決まった時点で制御アダプタを足せる構成にしてあります。

出典：一般社団法人日本卸電力取引所 (JEPX)

---

## なぜバックテスタから作るのか

予測モデルを先に作ると、精度を上げても**それが何円になるのか分からない**という問題に当たります。

先に「後知恵の理論上限」を出しておけば、以降すべての戦略を `理論上限の何%を取れたか` という単一の軸で評価できます。営業面でも同じで、対象セグメントが未定という弱点が「どのセグメントが儲かるか机上で比較できるツール」に変わります。

```
                      ┌─────────────────┐
JEPX CSV ──fetch──►   │  Parquet store  │  ──backtest──► 理論上限 (円/kWh/年)
                      └─────────────────┘                      │
                                                               ▼
                                              予測モデルの評価軸（Phase 2）
```

## クイックスタート

```bash
uv venv && uv pip install -e ".[dev]"

# 1. データ取得（年度ファイル単位。1日1回で十分）
jepx-arb fetch --year 2025 2026

# ネットワークが塞がれている環境なら、手元にDLしたCSVを直接投入
jepx-arb fetch --from-file ~/Downloads/spot_summary_2025.csv

# 2. 何が入っているか確認（価格スプレッドの分布）
jepx-arb stats --area tokyo

# 3. 単一構成のバックテスト
jepx-arb backtest --preset grid-2mwh --area tokyo --from 2025-04-01 --to 2026-03-31

# 4. ★ セグメント横断比較（最初に見るべきはこれ）
jepx-arb compare --areas tokyo kansai kyushu --from 2025-04-01 --to 2026-03-31
```

## 数字を読む前に知っておくこと

このツールが出す金額には、**必ず**以下の前提が付きます。外して引用すると嘘になります。

| 前提 | 内容 |
|---|---|
| **完全予見** | 48コマすべての価格を事前に知っている前提の最適解。**上限であって期待値ではありません。** 予測ベースの実運用はこの6〜8割程度に着地するのが一般的です。 |
| **スポットのみ** | 容量市場・需給調整市場・インバランスの収益を含みません。系統用蓄電池は実際には収益の相当部分をそちらで得ているため、`grid-2mwh` の数字は事業性を過小評価します。 |
| **プリセットは仮値** | capex、サイクル寿命、託送料金、小売マージンはすべて仮置きです。実際の見積りに差し替えるまで、出力を事業判断に使わないでください。 |
| **需要カーブは合成** | 逆潮流不可のケースでは放電量が需要に制限されます。同梱の需要プロファイルは形だけ合わせた合成データです。実測30分値が手に入った時点で差し替えてください（`load_series`）。 |

### 劣化コストの扱い

劣化コストは最初からモデルに入れてあります。入れないと最適化が「毎日フル充放電」を返し、現実と乖離するためです。

単位は **円/kWh（AC側の放電量あたり）** に統一してあり、価格スプレッド（円/kWh）と直接比較できます。ここから運用の閾値が出ます。

```python
spec.breakeven_spread_jpy_kwh(buy_price)   # この価格差を下回るなら動かすべきでない
```

`--capex 120000000 --cycle-life 10000` で見積りから逆算できます。


### 取得層を差し替え可能にしてある理由

JEPXの免責事項には「ご利用条件および公開されている情報の変更・削除は原則として予告なしに行います」とあります。明示的なスクレイピング禁止条項は見当たりませんが、**ある朝突然パースが落ちる前提**で設計すべきです。

そのため:

- HTMLパースはしません。表示はJavaScriptで切り替わるため脆いので、CSVダウンロードのエンドポイントを直接叩きます
- 必要な列が見つからなければ**明示的に落とします**（`SpotCsvFormatError`）。黙って壊れたデータを書き込むより、cronが赤くなるほうが安全です
- `ManualCsvSource` を常に用意しておき、自動取得が死んでも手動で回せるようにしてあります

商用化の際は、この層を有償APIに差し替えてください。規約リスクを事業の土台にしないためです。

## セグメント比較（`compare`）

4つのプリセットは「どの顧客層を狙うか」を数字で比較するためのものです。

| preset | 構成 | 料金 | 逆潮流 |
|---|---|---|---|
| `home-8kwh` | 家庭用 8kWh / 3kW | 市場連動＋12円 | 不可 |
| `home-8kwh-tou` | 家庭用 8kWh / 3kW | 時間帯別（夜間割引） | 不可 |
| `hv-500kwh` | 高圧自家消費 500kWh / 250kW | 市場連動＋6円 | 不可 |
| `grid-2mwh` | 系統用 2MWh / 1MW | 卸電力市場に直接参加 | 可 |

比較軸は **円/kWh(容量)/年**。これで8kWhの家庭用と2MWhの系統用を同じ表に並べられます。

`home-8kwh-tou` は市場価格と無関係な固定プランです。市場連動プランが**これを上回れるのか**を確認するためのベースラインとして入れてあります。

## データ取得の運用

**頻度は1日1回で十分です。** スポット市場は前日10時締切、13時頃に翌日48コマが確定するため、高頻度ポーリングで得られるものはありません。

同梱の GitHub Actions（`.github/workflows/fetch-spot.yml`）は毎日 14:00 JST に起動し、CSVを取得してParquetを更新し、同じリポジトリにコミットします。

この構成の利点:

- サーバー費用ゼロ、インフラ管理ゼロ
- **データの変更履歴がgitに残る。** JEPXが過去日を再公表した場合、差分で追えます
- 取得が失敗すればActionsが赤くなって気付ける

データ量は年間約17.5万行（48コマ×10エリア×365日）、Parquetで数MB。DBは不要で、DuckDBからParquetを直接クエリできます。規模が育ってからPostgresに移せば十分です。

```sql
-- DuckDB から直接
SELECT delivery_date, max(price_jpy_kwh) - min(price_jpy_kwh) AS spread
FROM 'data/spot/spot_prices_*.parquet'
WHERE area = 'tokyo' GROUP BY 1 ORDER BY spread DESC LIMIT 10;
```

## ロードマップ

| Phase | 内容 | 状態 |
|---|---|---|
| 0 | 取得＋Parquet蓄積（GH Actions） | ✅ |
| 1 | バックテスタ＋理論上限レポート | ✅ |
| 2 | LightGBM予測 → 予測ベースのバックテスト | 未着手 |
| 3 | MILP最適化（起動制約・同時充放電の排除） | 未着手 |
| 4 | FastAPI＋ダッシュボード | 未着手 |
| 5 | 制御アダプタ（ECHONET Lite / Modbus） | **対象確定後** |

Phase 2 で使う無料データ:

- 実績価格（本リポジトリ）
- 気象庁の過去・予報データ
- 各送配電事業者のでんき予報（需要・太陽光出力）

Phase 5 に着手しないのは意図的です。低圧か高圧か系統用かで通信方式（ECHONET Lite / Modbus）も収益規模も必要台数も変わるため、対象が決まるまで実装は無駄になります。データ取得と分析はどのルートでも共通なので、そこだけ先に作ってあります。
